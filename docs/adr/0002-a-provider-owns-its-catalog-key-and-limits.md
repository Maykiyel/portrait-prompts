# A Provider owns its catalog, its key, and its limits

An image vendor is described by one object, a Provider, which owns three things nobody else may know: which models it offers, whether its key is present, and which image shapes it can produce. A registry maps a provider id to that object. The generation run is handed a Provider and names no vendor, exactly as it is handed a Generator today; the registry is imported only by the composition roots, which already named one vendor each and may name two. We considered describing vendors only by their capabilities, with the catalog mapping a model id to a generator and a set of allowed sizes and no provider id anywhere above it, and rejected it: capabilities cannot be enumerated without naming whoever owns them, so it moves the vendor name one file down without removing it, and pays for that with an opaque model id that cannot be read in a Manifest or a log line.

## Consequences

The rule that no vendor reaches the run is enforced by a check in the smoke audit, and that check must name every vendor rather than the first one it was written for. It was written when there was one, so its vendor half was a single package name; a second vendor in the run's import graph passed silently. A guard that stops guarding at the moment it first matters is worse than no guard, because it reads as coverage. The same check has to keep its other half, which catches a terminal write anywhere in the graph rather than only under the vendor's name.

A Provider declares its model ids in its own vocabulary, which means the provider's types live under `core/` and cannot be written in terms of the HTTP contract: the smoke audit forbids any module under `core/` from naming `api-types`, so the browser's `provider` field and the provider's own keys are separate types that agree by construction rather than by declaration. That is a deliberate cost and it buys the run's independence from the wire format, which is what lets the run be tested without an HTTP server.

A limit the Provider cannot meet is a refusal, not a substitution. One vendor can produce a shape at a resolution another cannot, and asking for the larger one there must fail with a message naming the actual limit, never quietly return the smaller image under the name of the larger — the app does not do anything other than what it was asked, and a resolution that silently drops is the same defect as a salt guard that silently resets. The refusal is also where the honest version lives: when the substitution would have been smaller than the equivalent tier elsewhere, the message says so.

Failure classification is the Provider's, and it is stated in data rather than in prose. The run's catch block reduces every error to a message string, so a failure that retrying cannot fix has no way to be told apart from one that a later run might clear; the type of the error is discarded before the decision is made. Terminal failures therefore cross the seam as a declared type carrying a code, beside the archive's own, so the run switches on the code and rewording a message cannot change behaviour. A provider's refusal of a prompt can be permanent — the prompt itself is refused — or a matter of the render, in which case the same prompt and seed may succeed next run, and the two must not share a terminal status or the second kind of failure is thrown away with the first.

Retry policy belongs to the Provider for the same reason classification does, and both vendor SDKs retry beneath it by default. Left alone, a fixed attempt count multiplies a hidden internal count, so a run whose account cannot bill spends its whole budget re-asking. The rate is also the Provider's to state: what it will accept per minute is a fact about the vendor, so the run's concurrency is clamped to it and says so when it clamps, rather than discovering the ceiling through a wall of failures.

Key presence is reported per provider as a boolean, and the key itself never leaves the server. A run is refused when the Provider it was asked for has no key, which is the one gate that has to stay outside the run, because it is a question about the environment the run was started in rather than about the Seed being generated.

The Manifest records which provider made an image beside which model, because a bare model id implies its vendor by string convention rather than by data, and a Manifest that has to be pattern-matched to be read is not provenance. Rows written before this decision have no provider, and they are read as the vendor that was the only one available at the time — that is a fact about those rows, not a guess about them, and the default is applied in the one module that reads the Manifest and nowhere else.
